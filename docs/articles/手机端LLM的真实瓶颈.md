# 手机跑本地大模型，瓶颈根本不是内存

> 这是我在做一个 Android 端侧 LLM 聊天应用时的实测记录。代码开源在
> [local-ai-assistant](https://github.com/zhenglei9527/local-ai-assistant)。
>
> 结论可能和你的直觉相反，而且我一开始也判断错了。

---

## 一开始的假设：内存不够

做端侧推理，第一反应是「手机内存太小」。于是我按这个思路设计：

- 读取设备内存
- 估算模型运行时占用（权重 + KV cache）
- 只推荐装得下的模型

为了做这个估算，我需要算 **KV cache 有多大**。这是推理时缓存注意力 Key/Value 的地方，随上下文长度线性增长。

我当时的公式是：

```
KV = layers × kv_heads × head_dim × ctx × bytes_per_elem
```

Qwen3-4B 代入：36 层 × 8 KV head × 128 head_dim × 32768 上下文 × 2 字节 = **约 1.13 GiB**

看起来完全能接受。于是我在设计文档里写下：

> 内存不是瓶颈。32K 上下文在 8GB 机器上完全可行。

**这个结论错了，而且是两个层面的错。**

---

## 错误一：我算错了 4 倍

公式漏了一项。注意力有 Key **和** Value 两份缓存：

```
KV = 2(K+V) × layers × kv_heads × head_dim × ctx × bytes_per_elem
```

修正后，Qwen3-4B 在各上下文大小下的 KV cache：

| 上下文 | f16 | q8_0 |
|---|---|---|
| 4K | 0.56 GiB | 0.28 GiB |
| 8K | 1.12 GiB | 0.56 GiB |
| 16K | 2.25 GiB | 1.12 GiB |
| **32K** | **4.50 GiB** | 2.25 GiB |

**我漏掉的那个 2，让结论从「装得下」变成「装不下」。**

拿 8GB 手机（可用预算约 5.44 GiB）跑 Qwen3-4B Q6_K（权重 3.08 GiB）实算：

| 上下文 | 量化 | KV | 合计 | 结果 |
|---|---|---|---|---|
| 4K | f16 | 0.56 | 3.89 | ✅ 余 1.55 |
| **8K** | f16 | 1.12 | **4.46** | ✅ **余 0.99** |
| 16K | q8_0 | 1.12 | 4.46 | ✅ 余 0.99 |
| 16K | f16 | 2.25 | 5.58 | ❌ 超 0.14 |
| 32K | f16 | 4.50 | 7.83 | ❌ 超 2.39 |

**8GB 机型的内存墙落在 8K 和 16K 之间。** 不是 32K。

> ⚠️ 这个错误是我在写测试时才发现的。教训：**算式里的常数项，每一个都要问一遍「这是什么」**。
> 我当时把 K/V 两份缓存和 f16 的 2 字节混为一谈了。

---

## 错误二：内存其实不是主要矛盾

修正算术后，我打算按内存上限来定上下文窗口。但真正跑起来才发现问题不在那儿。

**真正的墙是预填充（prefill）。**

大模型生成回复分两个阶段：

1. **Prefill**：把整段提示词读进去，建立 KV cache。计算密集，和提示词长度成正比。
2. **Decode**：逐字生成。访存密集。

第二阶段的 decode 速度，手机上大约 **8–15 tokens/秒**（3B 模型，CPU）。这个数字还行。

但第一阶段完全不同：

| 提示词长度 | @20 tok/s | @40 tok/s | @80 tok/s |
|---|---|---|---|
| 4,000 | 200 秒 | 100 秒 | 50 秒 |
| 8,000 | 400 秒 | 200 秒 | 100 秒 |
| **16,000** | **800 秒** | 400 秒 | 200 秒 |
| 32,000 | 1,600 秒 | 800 秒 | 400 秒 |

**一张带世界书设定的角色卡，轻松填满 8K–16K token。**

也就是说：用户点了发送，**要等 13 分钟才看到第一个字**。

这不是「慢」，这是「用户以为 App 卡死了，然后卸载」。

---

## 所以真正的约束是什么

两道门，取更严的那个：

```
内存  → 决定「能不能装下」   → 8GB 机型上限约 8K
时间  → 决定「用户愿不愿意等」→ 8K 提示词要等 100–400 秒
```

**两条线指向同一个答案：默认 8192 上下文。**

这就是为什么我把默认窗口设成 8K，而不是模型支持的 32K。**用最大值当默认值是在制造事故。**

---

## 怎么绕过 prefill 这道墙

结论是：**让固定前缀只 prefill 一次。**

一次对话里，内容分两类：

| 类型 | 内容 | 变化频率 |
|---|---|---|
| **固定前缀** | 角色设定、世界书、系统提示词 | 几乎不变 |
| **动态后缀** | 对话历史、用户新消息 | 每轮都变 |

如果每轮都把整个提示词重新 prefill，那 8K 前缀就要重算 400 秒 —— 无法接受。

llama.cpp（以及 `llama.rn`）提供了会话持久化：把处理过的 KV cache 存下来，下次直接复用。

```
首轮：prefill 全部 8K            → 400 秒（一次性）
次轮：只 prefill 新增的几十 token → 几秒
```

⚠️ **但这条路有个陷阱**：KV cache 的复用要求**前缀逐字节完全相同**。任何一个字节变了，缓存全部失效，退回全量 prefill。

这意味着：

- 前缀里**不能有时间戳、随机数**
- 世界书条目**不能在轮次之间重新排序**
- 世界书的**触发集合必须冻结**（新触发的条目会插进前缀中间，导致后半段全部失效）

我最后加了一个「激活集合冻结」机制：一轮对话开始时确定哪些世界书条目生效，之后不再变。

## 另外三个实测出来的坑

### 1. `Runtime.maxMemory()` 不能用

判断「这台设备能不能跑」时，很自然会想到 `Runtime.getRuntime().maxMemory()`。

**它返回的是 Java 堆上限（128–512 MB），不是物理内存。** 而模型权重是 native 分配，不计入 Java 堆。

用它做判断，结果是**所有模型都被拒绝** —— 包括 400MB 的小模型。

正确做法是 `ActivityManager.MemoryInfo.totalMem`（物理内存）和 `availMem`（可回收内存）。

### 2. 内存预算要留余量，但不是按比例

我最初用「物理内存 × 0.7」做可用预算，并且用 8% 相对容差处理设备报的内存差异。

**结果两端都错：**

- 6GB 档：8% 只有 0.48 GiB，**小于系统实际预留**，真机 6GB 机型会被降级
- 16GB 档：8% 有 1.28 GiB，**过宽**，会把 14.75 GiB 的读数推进 16GB 档

**内存预留是固定绝对量（约 0.5–0.8 GiB），不是比例。** 改成 1.35 GiB 绝对容差后两端都对。

我实测的小米 14 Pro（16GB 标称）`MemTotal` 报的是 **14.80 GiB**。如果用朴素的 `>= 16` 判断，这台 16GB 手机会被误判成 12GB 档。

### 3. 关于量化档位的取舍

不是「能塞下就用大模型」。

8GB 手机上，`Qwen2.5-7B Q2_K` 装得下，而 `Qwen3-4B Q4_K_M` 也装得下。**前者的输出质量更差。**

所以推荐算法加了一条**量化下限**（4 bit）：优先保证质量，而不是参数量。

---

## 总结

如果你也在做端侧推理，这几条可能有帮助：

1. **先算 prefill 时间，再算内存。** 前者通常更早撞墙。
2. **KV cache 公式别漏 K/V 两份。** 我漏了一次，结论反了。
3. **默认上下文窗口取小值。** 8K 而不是模型支持的 32K。
4. **固定前缀必须能缓存。** 否则每轮重算，体验直接崩。
5. **前缀稳定性是硬约束。** 任何时间戳、排序、随机性都会让缓存失效。
6. **内存容差用绝对值，不用百分比。**
7. **量化下限比参数量上限更重要。**
