## Phase 1 — 首次真实构建 + native 模块接线

**目标**：`npx react-native run-android` 在一台 arm64 真机上跑起来，并显示真实内存数字。

### 任务

1. **搭建工具链**：安装 JDK 17、Android SDK（API 35）、NDK、Android Studio。
2. **对齐版本矩阵**：逐一核对 `docs/architecture.md` §10.2 中所有「待验证」版本。**不要跳过这一步直接构建**——版本不匹配的错误信息通常与真实原因无关，会浪费大量时间。以 `node_modules/@react-native/gradle-plugin` 和 RN 0.83 官方模板为准。
3. **安装依赖并首次构建**：`pnpm install`。注意 `llama.rn` 的 `postinstall` 会下载 40 MB 的 native 库（含 SHA-256 校验）。
4. **注册 `PhoneLlmSystemPackage`**：在 `MainApplication.kt` 中加入包列表。
5. **修正 JS 侧接线**：确认 `memoryProbe.ts` 能拿到真实数值（不再是 `FALLBACK_SNAPSHOT`）。
6. **验证 `verifyNativeLibraries()`**：确认 `librnllama.so` 能被加载。

### 验收标准

- [ ] `pnpm android` 构建成功，无 Gradle / Kotlin 错误。
- [ ] App 在真机启动，显示 4 个 tab，无红屏。
- [ ] 设置页的引擎诊断区**显示真实物理内存**（与系统「关于手机」中的 RAM 数值一致，误差 < 5%）。
- [ ] 日志中**不出现**「rnllama 加载失败」。
- [ ] `adb shell dumpsys meminfo <pkg>` 中 native heap 在空闲时正常，无异常增长。
- [ ] **验证 `maxMemory()` 的陷阱**：在诊断页同时显示 `Runtime.maxMemory()` 与 `MemoryInfo.totalMem`，确认两者差异巨大（这是本架构 §7.1 的论据，值得亲眼确认一次）。
- [ ] Release 构建（`--variant release`）能安装并启动——**专门验证 ProGuard 规则生效**，因为 JSI 绑定被剥离的故障在 debug 下不复现。

## Phase 2 — MVP：能下载、能加载、能聊天

**目标**：用户可以下载一个模型、加载它、和一个通用助手（尚无角色卡）对话，流式输出。

### 任务

1. **实现 sha256 native 方法**（`PhoneLlmSystem.sha256(path)`）：分块 `MessageDigest`，返回十六进制。
2. **补齐 catalog 真实数据**：从各模型仓库取得确切的文件名、大小、sha256。**每一条都要逐字核对**——错误的 sha256 比缺失更糟。
3. **接线下载器**：`BackgroundModelDownloader` 与 store、DB 打通。
4. **端到端验证断点续传**：这是本阶段**最容易被跳过也最值得验证**的一项。
5. **接线推理引擎**：`useEngineStore` 驱动 `llamaRnEngine.ts`。
6. **聊天流式输出**：`streamingText` → `messages` 的落库时机。
7. **应用启动时 reconcile**：处理 DB 与磁盘不一致。

### 验收标准

- [ ] 下载一个 ≥ 1 GB 的模型成功，进度条平滑，速度显示合理（与实测网速量级一致）。
- [ ] **续传验证（关键）**：下载到约 50% 时，用「强制停止 App」+「重启 App」的方式中断，重进后确认**从断点继续**而非从 0 开始。检查磁盘上 `.partial` 文件的字节数与 DB 中的 offset 一致。
- [ ] **切后台验证**：下载中按 Home 键切走、锁屏 5 分钟，回来确认下载**仍在继续**（这是选择 native 下载器的全部理由）。
- [ ] **校验验证**：故意把 catalog 中某个 sha256 改一位，确认下载失败并给出「校验不匹配」提示，而**不是**静默通过。
- [ ] **磁盘不足验证**：确认开始下载前就拒绝并提示，而不是下到一半失败。
- [ ] 加载模型成功，加载进度条真实推进（不是假动画）。
- [ ] 流式输出逐字出现，**无卡顿**（在 60 Hz 下不掉帧）。
- [ ] 点「停止」能立即中断生成。
- [ ] **KV 清理验证**：会话 A 聊完，新建会话 B，确认模型**不会**提到会话 A 的内容。
- [ ] **内存闸门验证**：在 4 GB 设备上逐个模型确认判定准确——判为「过大」的模型**确实**加载失败或被杀，判为「合适」的确实能跑。**若判定与实际不符，必须重新校准 §7.2 的 256 MiB 额度。**
- [ ] 推理速度基线：在目标机型上记录 tokens/s，作为后续优化对照。
- [ ] 模型加载后 `adb shell dumpsys meminfo` 的 native heap 与 §7.2 的估算值处于同一量级（±30% 内）。

## Phase 3 — 角色卡系统

**目标**：SillyTavern 式的角色聊天体验。

### 任务

1. **实现 `parsePngCard()`**：遍历 PNG chunk，读 `tEXt`/`iTXt` 中的 `chara` 键（base64 编码的 JSON）。注意 `zTXt` 需 zlib 解压。
2. **角色卡导入 UI**：文件选择器 + 解析结果预览。
3. **提示词构造落地**：把 `promptBuilder.ts` 接到真实的推理调用。
4. **角色编辑**：内置的角色卡编辑器。
5. **开场白选择**：`first_mes` + `alternate_greetings`。
6. **重roll / swipe**：`messages.swipes` + `swipe_index` 已在 schema 中就位。

### 验收标准

- [ ] 导入一张真实的 SillyTavern V2 PNG 角色卡成功，显示名称、描述、开场白、头像。
- [ ] 导入 V1 格式的卡也能成功（自动升级）。
- [ ] 导入损坏 / 非角色卡的 PNG **不崩溃**，给出明确错误。
- [ ] 角色卡导入后，对话中模型**确实**采用角色的人设（可通过询问其姓名/背景验证）。
- [ ] 开场白自动作为第一条 assistant 消息插入。
- [ ] 有多个开场白时可以在新会话中选择。
- [ ] 重roll 产生新回复，且可通过回退按钮切回上一版。
- [ ] **Prompt 构造验证**：在设置中可查看实际发送给模型的完整 prompt，确认角色块、系统提示、历史消息顺序正确（这是调试角色扮演问题的主要手段）。
- [ ] 编辑历史消息后，确认 KV cache 被清空（下一轮响应变慢是**预期**行为）。

## Phase 4 — 完整版：酒馆级特性

**目标**：功能对齐 SillyTavern 的核心能力。

### 任务

1. **世界书 / Lorebook**：关键词触发的上下文注入。
2. **上下文长度管理**：自动截断策略、对话摘要。
3. **作者注释 / 深度注入**：按深度插入的提示。
4. **多角色群聊**：两个以上角色交替发言。
5. **表情 / 立绘**：按关键字切换头像。
6. **正则脚本**：对模型输出做后处理。
7. **模型参数预设**：保存/切换采样参数组合。
8. **导入导出**：会话与角色卡的备份。
9. **流式朗读（TTS）**：llama.rn 已内置实验性 TTS 支持（OuteTTS 等）。

### 验收标准

- [ ] 世界书条目在关键词命中时被注入，未命中时不注入（可通过 prompt 查看器验证）。
- [ ] 会话超过上下文长度时**自动管理**，不报错也不丢失最近对话。
- [ ] 群聊中多个角色能区分彼此发言，不混淆身份。
- [ ] 采样参数预设切换后，生成风格有可观察的变化。
- [ ] 导出 → 清除数据 → 导入，会话完整恢复（含角色卡关联）。
- [ ] 长会话（100+ 轮）下内存占用**不持续增长**（验证 KV cache 与消息分页均无泄漏）。

## Phase 5 — 打磨与性能

**目标**：从「能用」到「好用」。

### 任务

1. **GPU/NPU 加速**：OpenCL（Adreno 700+）、Hexagon（SM8450+），含设备探测与优雅回退。
2. **提示词缓存复用**：最大化 KV prefix 命中率。
3. **模型 catalog 运行时刷新**：远端 index.json + 本地缓存。
4. **低内存策略**：`no_extra_bufts`、KV 量化、动态上下文。
5. **UI 打磨**：动画、深色主题细节、无障碍。
6. **错误上报**：本地日志（**不含对话内容**，隐私优先）。

### 验收标准

- [ ] 在支持的机型上 `context.gpu === true`，且在诊断页**如实显示**实际后端（回落时显示原因）。
- [ ] 启用 GPU 后 tokens/s 相对 CPU **有可测量提升**（记录前后数字）。
- [ ] 连续对话第二轮起明显更快（KV prefix 复用生效，可从 timings 的 `cacheReusedTokens` 确认）。
- [ ] 在不支持 GPU 的设备上**不崩溃**，自动回落且提示清楚。
- [ ] 更新远端 catalog 后新模型出现在列表中，无需更新 App。
- [ ] 所有交互元素 ≥ 48dp 触控区域。
- [ ] 崩溃日志中**不含**任何对话文本或角色卡内容。

## 通用风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **llama.rn 是 RC（0.13.0-rc.3）** | API 可能破坏性变更 | 已隔离在 `llamaRnEngine.ts` 单文件；升级前先跑 Mock 引擎的契约测试 |
| **无 Android 经验** | 卡在构建/Gradle 环节 | Phase 1 单独成阶段，不混入功能开发；优先用官方模板对照 |
| **机型碎片化（内存）** | 判定不准导致 OOM kill | Phase 2 必须在真实低端机上校准，不能只看旗舰机 |
| **模型文件巨大** | 下载失败率高、用户流失 | 下载器的六条不变量必须严格执行，尤其是校验；失败要给出可操作提示 |
| **DNS 污染（huggingface.co 不可达）** | 开发期无法核实模型数据 | 开发机上配好代理；或在能访问的机器上生成 catalog JSON 后导入 |
| **sha256 占位符未替换** | 校验形同虚设 | Phase 2 明确列为阻塞任务；`isPlaceholderDigest()` 会在日志中暴露 |
| **隐私** | 本地聊天记录泄漏 | `allowBackup="false"` 已设；错误的日志上报策略会破坏这一保证，Phase 5 需专门审查 |

## 里程碑定义

- **M1（Phase 1 结束）**：App 能构建、能启动、能读到真实内存。**这是从「设计」到「工程」的分界点。**
- **M2（Phase 2 结束）**：能下载模型并完成一次真实对话。**这是最小可用产品。**
- **M3（Phase 3 结束）**：能用角色卡扮演。**这是「类 SillyTavern」的起点。**
- **M4（Phase 4 结束）**：功能对齐 SillyTavern 核心能力。
- **M5（Phase 5 结束）**：性能与体验达到可发布标准。
