## 分片命名规律

所有分片严格遵循：

```
<basename>-<5位序号>-of-<5位总数>.gguf
例：qwen2.5-7b-instruct-q4_k_m-00001-of-00002.gguf
```

已对全部 180 个分片文件做过校验：

- 每组的序号恰好是连续的 `1..N`，无缺号、无重号
- 每组的分片数与文件名中的总数一致
- 校验失败数：**0**

**接入提示**：分片总数不固定，不能按固定体积推算（同为 32B 的 fp16，
`Qwen2.5-32B-Instruct` 是 17 片而 `Qwen2.5-Coder-32B` 是 9 片）。必须从文件名或接口读取。
另有部分仓库（`Qwen2.5-14B-Instruct`、`Qwen2.5-32B-Instruct`）**只提供分片文件**，
不存在未分片的单文件，App 不能假设单文件一定存在。

## 命名陷阱

1. **大小写不统一**：Qwen3 系列是驼峰式 `Qwen3-4B-Q4_K_M.gguf`，
   Qwen2.5 系列是全小写 `qwen2.5-7b-instruct-q4_k_m.gguf`。
   任何硬编码或大小写不敏感匹配都会失败。**请一律使用 JSON 里的 `fileName` 原值。**
2. **同一量化可能有两套文件**：`Qwen2.5-Coder-*` 系列部分量化档同时存在未分片单文件
   和分片副本（体积相差几 KB 的容器填充）。本清单已去重，保留分片版（分片可逐片续传，更适合移动网络）。
3. **sha256 为 null 是正常的**：接口针对**每个分片文件**各给一个哈希，没有「合并后整模型」的哈希。
   分片模型的哈希请看 `shards[].sha256`；非分片模型 `sha256` 已填实值。

## 内存估算口径

```
最低内存 = 权重体积 × 1.12 + 0.35 GB   # 运行时开销
推荐内存 = 权重体积 × 1.35 + 0.90 GB   # 预留 KV cache 余量
```

这是启发式估算，未考虑具体上下文长度、KV cache 量化与后端实现差异。
接入时应按真机实测调整，不要把它当成硬性约束。
